# Provider verification and bounded recovery · RIID-5822/5823

[Runtime policy source](provider-recovery.riido.json) implements the safe pre-dispatch subset of the [shared recovery design](https://github.com/teamswyg/riido-contracts/blob/main/docs/20-domain/provider-recovery.md).

Runtime actors probe compatibility and authentication outside their mailbox. One probe per provider is allowed; Status returns the last observation immediately and admission can wait in a finite queue. Cancel/Stop and other providers remain responsive. Only a completion with the current generation and captured environment fingerprint is applied. Unknown authentication preserves running session identity; confirmed binary drift still fences pinned sessions. Probe success does not mean a task or model invocation succeeded.

RIID-5900 separates probe availability from the verified identity of an ongoing session. An inconclusive authentication or version probe, or an adapter probe error, denies new submissions while preserving running sessions only when no executable identity change was observed. Codex version probes require a successful exit and a nonempty stdout version; stderr warnings are not part of version identity. Confirmed login-required still stops existing work with the existing provider-blocked outcome and an authentication-required reason. It cannot silently keep a logged-out session alive, and concurrent executable, content-hash or confirmed version drift retains runtime-pin fencing. Neither case replays work, refreshes credentials or changes permissions.

The supervisor can retry only a typed failure known to occur before a provider process starts. Default policy permits three attempts within 30 seconds; the maximum is three within 60 seconds. Normal first workspace materialization uses the assignment lifetime context and pauses only this recovery elapsed clock; it cannot be cut short by the default 30-second provider budget. Preparation preserves the remaining budget rather than resetting it, remains cancellable and retains any explicit host-binding preparation limit. Provider verification, journal acknowledgement, admission, backoff and handoff still consume the finite recovery budget. Login, quota, authorization, cancellation and any dispatched or unknown outcome never cause automatic replay. Backoff has jitter and respects the total deadline. A provider/environment circuit opens after two failures, permits one half-open owner, and closes on confirmed provider completion. Tracking is bounded to 64 scopes.

A newly claimed, definitely unstarted execution is retained locally before its Ready report. It keeps the original runtime lease heartbeat and cancellation watch while Ready runs outside the supervisor mailbox. Transient transport failures may retry the same Ready payload and lease-scoped deterministic key at most three supervisor attempts within 30 seconds, separately from provider recovery attempts; the existing HTTP retry stays inside each attempt. The server acknowledgement must match schema, event identity, Ready state, stable key and durable event sequence/time. Missing authority, malformed acknowledgements and permanent authentication/lease rejection never dispatch. Exhaustion produces a bounded terminal result through the existing durable-report retry path. Cancel, stop, runtime drift and obsolete claim-context completion fence Ready before provider admission; a late reply cannot revive a finished or replaced pending claim. This local proof never permits a fresh daemon process to replay a no-session active assignment. New `ready:` keys carry the lease token only for server-side validation and its removal before append/ACK. Deploy that control-plane validator before this Daemon; legacy sequence keys remain compatible.

Cross-provider handoff requires an explicit backend-authorized provider/model candidate. The same assignment, authorized prepared directory and permission scope are retained. Native resume, provider-specific environment/arguments/MCP configuration or unsupported required surfaces prevent handoff. The target must be on the same daemon/owner/device, expose the approved model and pass capability eligibility. Its instructions are regenerated from the original provider-neutral input. A foreign native session ID is never passed to it.

Each attempt and switch requires a synchronous existing Riido-log acknowledgement under the original assignment lease before dispatch. The event carries only bounded recovery fields and a deterministic idempotency key. Its lease token is transport-only and must be removed by backend validation before storage/logging. Fallback native session IDs remain in the local provenance index and are never pinned to the original provider assignment, including its terminal payload. Recovery outcome journals use the Riido-log event; terminal delivery keeps the existing contract and is not blocked by an outcome-journal delivery failure.

Original runtime ownership continues renewing the assignment during preparation, backoff and target execution. Target native activity does not renew the same assignment under a different runtime lease.

Dispatched means started, never recovered. Ordinary first-attempt completion stays dispatched/confirmed and is not counted as a recovery. Only a successful retry or handoff followed by confirmed provider protocol completion becomes recovered; host verification and semantic task completion remain separate. Existing host verification/correction rules continue to apply. The admission deadline is separate from the authorized run lifetime so successful admission does not immediately cancel a running task.

Codex model rejection is a user-action block when its structured error code is `model_not_found` or `unsupported_model`, or its message matches the native ChatGPT-account unsupported-model diagnostic. It does not become an authentication failure or a transient retry. The existing bounded `provider_blocked` / `check_provider` execution diagnostic is retained; a general HTTP 400 or an unknown upstream failure is not enough to infer this cause. Process-started model rejection never enables automatic replay or provider switching.

Cancellation watches carry their original claim context into the supervisor mailbox. They cancel only that captured context directly; provider cancellation by task identity occurs only after the supervisor verifies that the same claim still owns the task. A delayed old watch cannot stop a replacement claim reusing that task ID.

No CLI update, authentication refresh, provider process restart, permission widening, post-dispatch replay or fresh restart recovery is introduced. Stateless active assignments without durable session continuity continue to be skipped. Tests use deterministic process/adapter fixtures; they do not claim a fresh real-account/model experiment.

Recovery cancellation fixtures synchronize both cancellation-watch registration and the first backoff journal boundary before cancelling. A buffered progress record is historical evidence and cannot establish that the recovery loop is still waiting when the test consumer reads it. A separate timer-wait regression verifies prompt cancellation. This test synchronization does not change production backoff durations, deadlines, retry budgets or cancellation behavior.
